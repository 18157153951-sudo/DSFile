# 内核与风险

本文讲清楚三件事：**这套东西是什么**、**点「激活」之后到底发生了什么**、**有哪些风险，以及我们刻意不做的事**。

事实来源：`Sources/Core/DSKernel.{h,m}`、`Sources/Core/DSCredEscape.{h,m}`、`Sources/Core/KernelCenter.swift`、`FilzaTweak/NOTICE.md`、`FilzaTweak/sandbox_escape.m`、`FilzaTweak/kexploit/offsets.m`。凡本文没写死的细节，**以源码为准**。

---

## 一、这套东西是什么

myfilza 走的是 **免越狱路线**：不修改系统分区、不装越狱环境、不注入别的进程，而是利用一个**公开的 DarkSword 内核漏洞**（配合一次沙盒逃逸）来让 **myfilza 自己的这个进程**获得整机文件系统的读写能力。

| 项目 | 说明 |
| --- | --- |
| 漏洞来源 | 公开的 DarkSword 内核漏洞实现（34306/FilzaJailedDS 的 `kexploit_opa334`、`krw`、`kutils`、`offsets` 等），本仓库锁定上游 **tag 2.2**，来源与作者见 [FilzaTweak/NOTICE.md](../FilzaTweak/NOTICE.md) |
| 沙盒逃逸 | 不用上游那条 `proc_self()` 路线（本机 socket 的 `so_background_thread` 恒为 0，它会野读 0x378 并让 App 直接退出）。改用 `Sources/Core/DSCredEscape.m`：**两个 socket 的 `so_cred` 指向同一对象 + `cr_uid == getuid()` 复核** 定位本进程 `ucred`，再走 `ucred → cr_label → sandbox → ext_set`，照上游的三步改写扩展（路径改成 `/`、类别改成 `com.apple.app-sandbox.read-write`、补满 16 个 hash 槽） |
| 作用范围 | **只有本进程**。改的是本进程内存中的沙盒扩展数据（`ucred` / `label` / `sandbox` 结构），不是系统全局配置 |
| 持久性 | **一次进程生命周期**。进程一死（包括被系统回收、被杀、重启设备）就没了，下次冷启动必须重新激活 |
| 触发方式 | 用户在设置页点「激活内核访问」。默认**不**自动执行；只有你自己打开「启动时自动激活」开关后，App 冷启动才会自动尝试一次 |
| 需要越狱吗 | 不需要。这也是它和「越狱插件」的根本区别——它不改系统文件、不装东西、不留后台 |

> **它不是越狱。** 不会给你一个持久的 root shell，不会改系统分区，不会让别的 App 获得任何能力。关掉 myfilza，一切归零。

## 二、激活流程的通俗解释

### 2.1 三个事实层面的东西

1. **内核读写（KRW）**：跑一次内核漏洞，拿到「能读写内核内存」的能力（代码里用 `gExploitDone` 记录「本次进程已经拿到过」）。拿到之后才能去改沙盒相关的内核数据结构。
2. **沙盒改写**：有了内核读写，把本进程的沙盒扩展表改成「可读写任意路径」（代码里用 `gEscaped` 表示最终成功）。
3. **自检**：不信任任何缓存标记，**真的去写一个文件试试**——`ds_probe_write_access()` 依次尝试 `/var/mobile/.dsfile_probe`、`/var/tmp/.dsfile_probe`，能 `open(O_WRONLY|O_CREAT|O_TRUNC)` 成功就立刻 `unlink` 掉并返回成功。写盘探针过了才认为逃逸成功。

### 2.2 点「激活」之后的完整分支

入口是 `DSKernel.activateWithLog:`（Swift 侧由 `KernelCenter.activate()` 在后台队列调用，因为它是**同步阻塞、可能耗时数秒**的，期间界面会卡住，这是正常的）。

```
点「激活内核访问」
        │
        ├─ 已在执行中？ ────────────────→ 返回「忙」，忽略这次请求
        │
        ├─ 本进程已逃逸？ ──────────────→ 返回「已经是逃逸状态」，什么都不做
        │
        ├─ 系统版本不在 17.0 – 26.0.x？ ─→ 返回「不支持」，并在设置页显示红字原因
        │                                   （不会去跑漏洞）
        │
        ├─ 内核读写已经拿到过？ ────────→ 只补做「沙盒改写」这一步（不重跑漏洞）
        │
        └─ 都没有 ──→ 跑内核漏洞 kexploit_opa334()
                        │
                        ├─ 返回非 0 ────→ 「漏洞失败」：通常是系统版本/机型不在 offset 表内
                        │                  （设备没有重启就已经是最好的结果）
                        │
                        └─ 返回 0 ──────→ 记下 kernel base，然后走「沙盒改写」
                                            │
                                            ├─ 改完 + 探针写盘成功 ──→ 「已激活」，可以读写整机
                                            │
                                            └─ 改完但探针失败 ───────→ 「内核已就绪（沙盒未通）」
                                                                        多数情况是 DAC 权限问题，
                                                                        可以去试一次「提权到 root」
```

### 2.3 四条失败分支分别是什么

| 分支 | 状态文案 | 含义 | 你可以做什么 |
| --- | --- | --- | --- |
| **不支持** | 不支持 | 系统版本不在 DarkSword 覆盖区间（`>= 17.0 && < 26.1`），或芯片是 A19 / A19 Pro / M5（`supportSummary` 明确提示覆盖不到） | 换设备/系统；或自己移植 offsets（见 [构建与安装.md](构建与安装.md) 第五节） |
| **漏洞失败** | 激活失败 | `kexploit_opa334()` 返回非 0，典型原因是机型/系统版本不在 offset 表内 | 先看诊断信息里的系统版本 + 芯片是否与支持范围匹配；可以再试一次；**别反复猛点**（每次都是一次真实的漏洞尝试） |
| **沙盒改写失败** | 激活失败 / 内核已就绪（沙盒未通） | 内核读写拿到了，但 `DSCredEscapeSandbox()` 后探针写盘仍失败 | 点「重试沙盒改写」——**它不会重跑内核漏洞**；仍不行就试「提权到 root」（看日志里的失败码：-1 没定位到 cred、-2 链路断了、-3 改写后探针仍写不进、-4 一个扩展都没改到） |
| **可单独重试** | 内核已就绪（沙盒未通） | 漏洞结果保留在 `gExploitDone`，所以沙盒那一步可以反复重试 | 见上 |
| **可提权到 root** | 设置页「提权到 root」 | 改写本进程 `ucred` 里 `posix_cred` 的 uid/gid（cr_uid/cr_ruid/cr_svuid 置 0、rgid/svgid 置 0），让 `getuid()` 变 0 | 只在「写 root 文件被拒」时才需要；**失败不影响已经拿到的沙盒逃逸** |

### 2.4 设计上的三条硬规矩

来自 `DSKernel.h` 顶部的注释，也是这套实现最值得说的部分：

1. **内核漏洞只在用户主动触发时执行一次，重复执行会被拦下**（二次利用极易 panic）。所以 `gExploitDone` 一旦为真，后续「激活」只会去补沙盒改写那一步。
2. **漏洞成功但沙盒改写失败时，允许只重试沙盒改写这一步，不重跑漏洞**（`retrySandboxEscapeWithLog:`）。
3. **所有能力都有自检（探针写文件 + `getuid()`），不做「装作成功」**。设置页还有「现场自检文件系统」，随时可以做一次不读缓存的真实写盘探针。

另外，内核漏洞只会 `printf`/`NSLog`，所以 `DSKernel.m` 里专门做了一套 stdout/stderr 捕获（`pipe` + `dup2` + `dispatch_source`），把这些输出逐行转成界面日志并落到会话日志文件里——**这是排查激活失败唯一有效的材料**。

### 2.5 提权到 root 是什么、代价是什么

- 做的事：现场重新定位本进程 `ucred`（不信缓存，且复核 `cr_uid == getuid()`），把 `posix_cred` 里的 `cr_uid` / `cr_ruid` / `cr_svuid` / `cr_groups` / `cr_rgid` / `cr_svgid` 改成 0，然后看 `getuid()` 是不是 0。
- **加固（0.3.0 起）**：执行前先过就绪校验（`rwSocketPcb` / `controlSocketPcb` / `g_kernel_base` 必须是合法内核地址）；**每一次写入前都过统一的地址闸门**（内核地址 + zone 段 + 对齐），被拒绝就立刻停手；写完把 6 个字段**回读**进日志，证明到底改成了什么。未激活时点它只会提示「请先激活内核访问」。
- 只在「沙盒逃逸已经成功、但某些 root 拥有的文件仍然写不进去」时才需要。**失败不会破坏已经拿到的沙盒逃逸**（设置页的说明里也是这么写的）。
- 代价与取舍：uid 变成 0 之后，**有些系统组件对 root 进程反而更严格**（可能出现「以 mobile 能读、以 root 读不了」这类反常现象）。所以它是「遇到具体问题时的补救手段」，不是推荐默认开的东西。
- 另外，myfilza 大量写操作并不依赖 root：`FileOperations` 在权限被拒时会用内核接口直接把 on-disk owner 改成 `mobile:mobile` 再重试（`DSKernel.setOwner(path:uid:501,gid:501)` 走 `apfs_own`，绕过 DAC），这条路通常比提权更「温和」。

## 三、风险清单

### 3.1 内核 panic → 设备重启（不可回滚）

**这是最需要正视的一条。** 内核漏洞利用本身有概率导致设备重启（内核 panic）。

- 触发时机：主要在执行内核漏洞的那一刻（也可能在改内核结构时）。
- 后果：设备黑屏重启；**正在编辑但没保存的东西会丢**；已经写进磁盘的改动不会因此回退；没有保存的工作丢掉就没了。
- 无法回滚：这是内核层面的失败，**备份和回滚救不了它**（备份只覆盖文件内容）。
- 概率说明：源码和上游 NOTICE 都只说「有概率」，**没有给出量化概率**。任何声称「多少百分比」的说法都是编的。
- 降低风险的做法：
  - 动手前先保存手头工作、确认重要数据已有备份；
  - 系统/机型明显不在支持范围时**不要硬试**（App 已经会拦住版本不符的情况）；
  - 激活失败后不要连续猛点（每次都等于一次新尝试）；
  - 别在电量告急、正在做重要事情的时候跑。

### 3.2 版本 / 机型不在 offset 表

- `offsets_init()` 的门槛是 `SYSTEM_VERSION_GREATER_THAN_OR_EQUAL_TO(@"17.0") && SYSTEM_VERSION_LESS_THAN(@"26.1")`，不满足会直接 `printf` 一行错误再 `exit(EXIT_FAILURE)`。
- 门槛之内仍然要看**具体版本区间 + CPU family**：`offsets.m` 里是按 `17.0` / `17.1-17.3` / `17.4-17.7` / `18.0` / `18.1-18.3` / `18.4-18.5` / `18.6-18.7` / `26.x` 等区间分块赋值，并且对 A12 / A13+ / A15+ / A16+ / A17+ / A18+ / M 系列分别走不同分支。落在某个区间的边界外（或者是你所在版本刚发布、上游还没补 offset）就可能失败。
- 芯片识别：`DSKernel.cpuFamilyName` 覆盖 A10 – A19 Pro / M1 – M4；**A19 / A19 Pro / M5 被 `supportSummary` 明确标为「该芯片暂未被漏洞覆盖，激活大概率失败」**（M5 不在映射表里，会显示成 `未知 (0x........)`）。
- 好消息是：这些情况的表现是**明确的失败提示**，不是「装作成功」。App 会告诉你原因，而不是让你在不知情的状态下以为已经逃逸。

### 3.3 提权后行为变化

见 2.5：uid=0 之后部分系统组件对 root 进程更严格，可能出现原本能做的事反而做不了。提权是可选动作，遇到具体问题再试。

### 3.4 只读系统卷写不进去

- `/System`、`/usr`、`/Applications` 等被 SSV（签名系统卷）保护。
- 沙盒逃逸解决的是「沙盒权限」，**不解决签名卷的只读挂载**——这是两回事。
- 实际表现：**能读、不能写**（写会失败并给出系统错误）。这是系统机制，不是本工具的缺陷，也不是「激活没成功」。
- 想确认「到底是没逃逸还是碰上只读卷」：设置页 → 诊断 → 「现场自检文件系统」，探针写的是 `/var/mobile/` 和 `/var/tmp/`（可写区域）。探针过了说明逃逸没问题，写不了的就是被 SSV 保护的位置。

### 3.5 改别人 App 的合规边界与后果

技术能力和「该不该做」是两件事：

- **只管理你自己设备上的数据。** 替换他人 App 的文件之前，请确认你有权这么做（软件许可、与权利人的约定、你所在地区的法律）。
- **别改主可执行文件**：在证书自签环境下，改过主可执行文件的目标 App 会因签名校验失败而**无法启动**；唯一可能仍能运行的例外是 TrollStore 安装的 App（ad-hoc 签名）。真改了就得重装那个 App。
- **myfilza 无法区分「你有权改」和「你无权改」**，它只是执行你写的步骤。判断和执行后果的责任在使用者。
- 分发问题：`FilzaTweak/` 的上游仓库**没有附带开源许可证**，本仓库的副本只供你自行构建、自行安装，不随任何公开分发。

### 3.6 其它值得知道的边界

| 风险点 | 说明 |
| --- | --- |
| 备份可能不完整 | 备份会话在**拷不动原件**时会退化成「登记了存在但没内容」的条目（`relativePath` 为空），回滚会提示「备份文件缺失」。所以备份不是 100% 保险，重要文件自己再留一份。 |
| 只读系统卷之外的写入也可能被 DAC 拒 | 这时靠「内核改属主」或「提权」解决；两条路都可能失败。 |
| Shell 脚本无备份无预演 | Shell 脚本直接交给 `/bin/sh` 跑，**没有预演、没有备份、没有回滚**。要可回滚就用配方脚本。 |
| 内核状态可能中途失效 | 逃逸状态是内存里的，某些系统行为（内存压力、子系统重启等）可能让它失效；设置页提供「重新检测」和「现场自检文件系统」来确认当前真实状态。 |
| 日志里有敏感信息 | 诊断信息和会话日志包含机型、系统版本、内核基址、路径。要公开贴出来之前自己判断。 |

## 四、我们刻意不做的事

下面每一条都是**行为承诺**，也是这份文档和这个 App 的边界。对照源码可以验证：`Sources/` 下没有任何 `URLSession` / `NSURLConnection` / `NWConnection` / socket 客户端代码，工程也没有联网相关的依赖。

| 不做 | 含义 |
| --- | --- |
| **不做后台常驻** | 没有后台任务、没有 `BGTaskScheduler`、没有常驻守护进程。App 不在前台就不干活；逃逸状态随进程结束而消失。 |
| **不做开机自启** | 不注册任何开机/登录启动项，不劫持 launchd，不装任何持久化组件。冷启动后要不要激活由你在设置页的「启动时自动激活」开关决定。 |
| **不联网** | 不发起任何网络请求，不上传任何东西（没有遥测、没有崩溃上报、没有检查更新）。所有数据都在 App 自己的 Documents 里。 |
| **不把漏洞用于任何其它进程** | 沙盒改写只改**本进程**的沙盒数据；提权只改**本进程**的 ucred。不改别的 App 的沙盒、不注入、不 hook、不跨进程提权。 |
| **不静默修改任何文件** | 所有写操作都是你主动触发（点按钮、跑你写的脚本），并且**都能在「记录」页看到**（运行历史 + 日志），被覆盖/删除的文件都会先进备份、可以一键回滚。没有「偷偷帮你改点什么」的逻辑。 |
| **不做任何隐蔽行为** | 没有隐藏开关、没有远程控制通道、没有按条件触发的后门逻辑。源码就是全部行为。 |

配套的三条自我约束（来自 `DSKernel.h` 注释，见 2.4）：漏洞只跑一次、沙盒改写可单独重试、能力必须自检通过才算数。

## 五、一句话总结

能力是真的（本进程可读写整机文件系统），边界也是真的（只读系统卷写不了、改主可执行文件会让自签 App 起不来、每次冷启动都要重来），风险也是真的（内核漏洞有小概率把设备搞重启，且不可回滚）。**把它当一把锋利的手工工具用：动手前先备份，动手后看记录，出事能回滚就回滚，回滚不了就重装。**

## 六、越狱 / 半越狱环境下的差异（0.3.1 起）

免越狱不是唯一路径。启动后探测一次环境（`EnvironmentProbe`，结果缓存 30 秒，设置页可点「重新探测环境」）：

| 环境 | 认哪些标志 | 行为 |
| --- | --- | --- |
| 经典越狱（rootful） | `/Library/MobileSubstrate/MobileSubstrate.dylib` 或 `DynamicLibraries`；或 `/bin/sh` 可执行且当前是 root | 文件操作直接走 POSIX，**不需要**先跑内核漏洞 |
| rootless（Dopamine / palera1n） | `/var/jb/usr` 或 `/var/jb/bin` 存在 | 同上，越狱根记为 `/var/jb` |
| roothide | `/var/mobile/Library/roothide` 存在，或任意 `.jbroot-*` 目录 | 同上，`sh` 用 jbroot 下的 `/bin/sh` |
| TrollStore | `com.opa334.trollstore.plist`、`.TrollStore` 标记，或 `TrollStore.app` | 独立标记，可与上面类型并存 |

统一判断入口是 `EnvironmentProbe.hasFileSystemAccess()`：**内核逃逸已激活** 或 **实际能读写沙盒外路径**（真的建一个探针文件、真的列一下目录），二者之一成立即视为有权限。因此：

- **未越狱**：行为与之前完全一致，必须先点「激活内核访问」；
- **越狱 / roothide / TrollStore**：设置页「环境」区块显示绿色徽章，文件页默认从 `/` 开始，「替换」页不再拦你；
- Shell 脚本用的 `sh` 会优先取越狱根里的（`/var/jb/bin/sh`、jbroot 下的 `bin/sh`），回退 `/bin/sh`；
- `getuid() == 0` 时设置页会标注「uid 0（root）」，写 root 属主文件不再需要额外提权；
- 越狱环境下**不做任何路径翻译**（rootless 的绝对路径本来就是 `/var/jb/...`，直接写就行）。
