# 脚本格式（配方 / Shell / 备份回滚）

本文只讲**格式与语义**，事实全部来自 `Sources/Scripts/` 下的源码：

| 文件 | 负责什么 |
| --- | --- |
| `Recipe.swift` | 配方 JSON 的数据结构、默认选项、占位符解析、官方模板 |
| `RecipeRunner.swift` | 前置检查、预演、执行、每个 op 的具体行为、Shell 运行器、目标解析 |
| `ScriptLibrary.swift` | 脚本库目录、导入/新建、payload 管理、Shell 模板 |
| `RunStore.swift` | 备份会话、`manifest.json`、运行历史、回滚 |

---

## 一、脚本库在磁盘上的样子

```
<App Documents>/
└── Scripts/
    ├── index.json                    ← 脚本清单（ScriptLibrary 自己维护，别手改）
    └── <脚本目录>/
        ├── recipe.json  或  run.sh   ← 脚本本体（文件名即 ScriptItem.fileName）
        └── payload/                  ← 要替换进目标 App 的文件
```

- `<脚本目录>` 由脚本名生成（`/` 会被换成 `-`；重名时自动加 `-1`、`-2`）。
- 脚本类型只有两种：`recipe`（配方，文件默认叫 `recipe.json`）和 `shell`（文件默认叫 `run.sh`）。
- 脚本目录可以整体「分享」出去，也可以整体导入回来。
- 因为工程开了 `UIFileSharingEnabled` 和 `LSSupportsOpeningDocumentsInPlace`，这个 `Documents` 目录在系统「文件」App 里可见，方便你用「文件」页直接往 `payload/` 里拷东西。

## 二、配方 JSON 完整格式

### 2.1 顶层字段

| 字段 | 类型 | 必需 | 默认 | 说明 |
| --- | --- | --- | --- | --- |
| `schema` | Int | 否 | — | 格式版本标记。官方模板写 `1`。**当前代码不读这个字段做校验**，只是备注用。 |
| `name` | String | 否 | `未命名配方` | 显示名（`displayName`）。 |
| `note` | String | 否 | — | 备注，会显示在脚本详情页「配方步骤」的页脚。 |
| `target` | Object | 否 | — | 目标 App 描述（见下表）。用了 `{app.*}` 占位符就必须能解析出目标。 |
| `options` | Object | 否 | 见 2.3 | 执行选项。缺省时逐项取默认值。 |
| `steps` | Array | **是** | — | 步骤列表。为空会被前置检查拦下（「配方里没有任何步骤」）。 |

`steps` 是唯一必需字段——整份 JSON 解不出来（字段类型不符等）时，脚本详情页会显示「解析 recipe.json 失败：...」。

### 2.2 `target`

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `bundleId` | String? | 优先按 bundle id 在已安装 App 里找（`AppScanner.app(withBundleId:)`）。 |
| `bundlePath` | String? | bundle id 找不到时按包体路径精确匹配（`AppScanner.app(withBundlePath:)`）。 |
| `dataPath` | String? | 数据容器路径。**只在「既没有 bundleId 也没有匹配到 App、只写了 bundlePath」这条兜底分支里才会被用到**（此时直接用你写的 `bundlePath` / `dataPath`，`executableName` 为空）。 |

目标解析顺序（`TargetResolver.resolve`）：

1. 用户在脚本详情页手动选了 App → **一律以手动选择为准**，配方里的 `target` 被忽略；
2. 否则用 `target.bundleId` 去找已安装 App；
3. 否则用 `target.bundlePath` 去精确匹配已安装 App；
4. 否则如果至少有 `target.bundlePath` → 用原始路径硬跑（占位符会退化成配方里写死的路径，`{app.executable}` 为空、`kill` 步骤会被跳过）；
5. 都没有 → 目标为 nil；此时如果步骤里用了 `{app.*}`，预演会报「配方里用了 {app.*} 占位符，但没有选定目标 App，或目标 App 找不到。」

### 2.3 `options`

| 字段 | 类型 | 默认 | 语义 |
| --- | --- | --- | --- |
| `backup` | Bool? | `true` | 开启备份会话。`replace`/`copy`/`move` 覆盖已有文件前、`delete` 删除前，把目标整份拷进备份会话；关掉后**没有任何回滚兜底**。 |
| `killTarget` | Bool? | `true` | 执行完文件步骤后，按可执行文件名结束目标 App 进程。**如果 `steps` 里已经写了 `kill`，这个开关不会再额外杀一次**。 |
| `stopOnError` | Bool? | `true` | 某一步失败后中止后续步骤。 |
| `fixOwnership` | Bool? | `true` | 写之前先调内核接口把**父目录**的属主改成 `mobile:mobile`（`FileOperations.makeWritable`），写完后再对目标自身做一次。需要已拿到内核读写。 |

> 这 4 个开关在脚本详情页是可视化 Toggle，改一下就会**写回 `recipe.json`**（用 `JSONEncoder` 的 `prettyPrinted + sortedKeys` 重新序列化，所以配方文件的排版会被规范化，键顺序会变）。
>
> 注意：`fixOwnership` 在 `chmod` / `chown` 步骤上不生效（那两步不调用它）；关掉它也不影响 `chmod`/`chown` 本身可用——它们会走内核接口或退回 `chmod(2)`/`chown(2)`。

### 2.4 `steps[]`

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `op` | String | **必需**。操作名，大小写不敏感（内部 `lowercased()`）：`replace` `copy` `move` `replaceDir` `mkdir` `delete` `chmod` `chown` `kill` `note` |
| `source` | String? | 源路径。`replace` / `copy` / `move` / `replaceDir` 必需；`note` 不用；其余忽略。 |
| `dest` | String? | 目标路径。**除 `kill` 和 `note` 外都必需**。 |
| `mode` | String? | 八进制模式字符串，如 `"0644"`。仅 `chmod` 必需；`"0o644"` 写法也接受（会把 `0o` 去掉）。 |
| `owner` | String? | 属主，如 `"mobile"`、`"mobile:mobile"`、`"501:501"`。仅 `chown` 必需。只写用户名时组名默认跟用户名一致。 |
| `note` | String? | 说明文本，仅 `note` 用；不写就是「说明」。 |
| `optional` | Bool? | `true` 时：`replace`/`copy`/`move`/`replaceDir` 的源不存在、或 `delete` 的目标本来就不存在 → 记为「跳过」而不是「失败」。默认 `false`。 |

## 三、占位符与路径解析

### 3.1 占位符表

`PlaceholderResolver.expand` 按下面的表做**纯字符串替换**（顺序无关，因为每个 token 都不同；替换是全局的，一行里可以出现多次）。

| 占位符 | 展开成 | 什么时候为空 |
| --- | --- | --- |
| `{app.bundle}` | 目标 App 包体路径，如 `/var/containers/Bundle/Application/<UUID>/WeChat.app` | 没解析出目标 |
| `{app.data}` | 目标 App 数据容器路径，如 `/var/mobile/Containers/Data/Application/<UUID>` | 目标没有数据容器，或没解析出目标 |
| `{app.bundleId}` | 目标 bundle id，如 `com.tencent.xin` | 同上 |
| `{app.name}` | 目标显示名（`CFBundleDisplayName` → `CFBundleName` → 目录名） | 同上 |
| `{app.executable}` | 主可执行文件完整路径（`包体路径 + / + CFBundleExecutable`） | 目标没解析出可执行文件名 |
| `{script.dir}` | 本脚本所在目录的绝对路径 | 永不为空 |
| `{script.payload}` | 本脚本目录下的 `payload` 目录绝对路径 | 永不为空 |
| `{docs}` | App 自己的 Documents 绝对路径 | 取不到时为 `""` |

拿不准实际会展开成什么：进脚本详情页，每个步骤都会把 `source` / `dest` **原样**列出来（显示的是占位符原文，不是展开后的值）；想看展开后的真实路径，跑一次**预演**，日志和结果里会带上解析后的完整路径。

### 3.2 `source` / `dest` 的相对路径规则

`PlaceholderResolver.resolvePath` 的逻辑只有三条：

1. 先展开占位符；
2. **展开后以 `/` 开头 → 原样使用**（绝对路径）；
3. 否则（相对路径）→ 拼到 `{script.dir}` 后面。

也就是说：

| 你写的 | 解析成 |
| --- | --- |
| `payload/config.json` | `<脚本目录>/payload/config.json` |
| `payload/sub/a.png` | `<脚本目录>/payload/sub/a.png`（子目录也支持） |
| `{script.payload}/config.json` | 同上 |
| `{docs}/foo.txt` | App Documents 下的 `foo.txt` |
| `/var/mobile/Library/Preferences/x.plist` | 原样 |
| `{app.data}/Documents/config.json` | 目标 App 数据容器下的路径 |

**注意**：相对路径永远相对**脚本目录**，不是相对当前工作目录、也不是相对 payload 目录。想指 payload 里的文件，就写 `payload/xxx`（或 `{script.payload}/xxx`）。

## 四、每个 op 的确切语义

所有 op 都会在预演/执行的日志里记一行 `[序号] op 摘要 → 状态（消息）`。状态有四种：`将执行`（预演）、`成功`、`跳过`、`失败`。

| op | 必需字段 | 预演（apply=false）做什么 | 执行（apply=true）做什么 |
| --- | --- | --- | --- |
| `replace` | `source`, `dest` | 检查源是否存在；判断目标是「新建」还是「将覆盖已有文件」 | 与 `copy` **完全等价**（代码里 `replace` 和 `copy` 走同一分支，只有 `move` 特殊）。目标存在 → 先备份再删掉旧的再拷。 |
| `copy` | `source`, `dest` | 同 `replace` | 同 `replace`。 |
| `move` | `source`, `dest` | 同 `replace` | 先备份 `dest`（如果存在），再 `FileManager.moveItem`（存在目标时先 `removeItem`）。**源文件会消失。** |
| `replaceDir` | `source`, `dest` | 检查源**目录**是否存在；报「将新建」或「将镜像覆盖整个文件夹（旧文件会被移除）」 | **镜像替换整个目录**：先 `session.capture(dest, recursive: true)` 把目标整棵递归备份，再删掉 `dest` 并把 `source` 整棵拷过去（`FileOperations.replaceDirectory`）。目标里源没有的旧文件会被移除；`dest` 原本不存在时登记 `existed: false`，回滚会把它删掉。 |
| `mkdir` | `dest` | 检查目录是否已存在 | 目录不存在才创建，`withIntermediateDirectories: true`（会连父目录一起建）。已存在则记为成功并提示「目录已存在」。 |
| `delete` | `dest` | 检查目标是否存在；不存在且 `optional` 不是 `true` → **失败**「目标不存在」 | 先备份目标整份，再 `removeItem`。日志写「已删除（原件已备份）」——注意：**只有 `backup: true` 时才真的有原件备份**。 |
| `chmod` | `dest`, `mode` | 只报计划，不校验文件是否存在 | `FileOperations.chmod`：先试内核接口 `DSKernel.setMode`，失败退回 `chmod(2)`；都失败才抛错。`mode` 必须是八进制。 |
| `chown` | `dest`, `owner` | 只报计划 | `FileOperations.chown`，`recursive: false`（**配方里的 `chown` 不支持递归**，属性面板里才支持）。先试内核接口，再退回 `chown(2)`。 |
| `kill` | — | 报计划「结束 <可执行文件名>」 | 用目标的 `CFBundleExecutable` 匹配进程并结束；没杀到 → 记「跳过」而不是失败。目标没有可执行文件名 → 跳过。 |
| `note` | `note`（可选） | **总是**记为「跳过」，消息就是 `note` 文本 | 同预演：不产生任何文件改动。 |

执行阶段的额外行为：

- **`fixOwnership` 生效点**：`replace`/`copy`/`move` 写之前对 `dest` 的父目录、写之后对 `dest` 本身；`mkdir` 对新建目录的父目录；`delete` 对目标的父目录。
- **`killTarget` 生效点**：所有文件步骤跑完之后，如果 `options.killTarget` 为真**且配方里没有 `kill` 步骤**，才按可执行文件名杀一次。
- **`stopOnError` 生效点**：某一步返回「失败」时立即 `break`，后面的步骤不执行（但备份会话照常提交，已经记下的原件仍然可以回滚）。

## 五、备份与回滚的确切语义

### 5.1 备份会话怎么写

开启 `backup` 时，执行开始前会 `RunStore.beginBackup(scriptName:targetSummary:)` 建一个会话：

```
<App Documents>/Backups/<yyyyMMdd-HHmmss>-<脚本名>/
├── manifest.json
└── files/
    ├── 001-<原文件名>
    ├── 002-<原文件名>
    └── ...
```

- 备份 ID 就是目录名（`<时间戳>-<脚本名>`，脚本名里的 `/` 会被换成 `-`）。
- `BackupSession.capture(path)` 登记一个即将被覆盖/删除的路径：
  - 同一路径在一次会话里**只登记一次**（重复 capture 直接返回 nil）；
  - 文件 → 整份拷进 `files/<3 位序号>-<文件名>`；
  - 目录 → `recursive` 默认为 `true`，整棵目录树拷进去；
  - **拷不动时**（比如权限不允许）会退化成「登记了存在但没内容」的条目，并写一条 warning 日志。这种条目回滚时**内容恢复不出来**，只能恢复 `mode`/`uid:gid`。
  - 路径不合法（空、非绝对路径）→ 直接不登记。
- 每条 `BackupEntry` 记录：`originalPath`、`relativePath`（相对 manifest 的路径）、`existed`（覆盖前是否存在）、`mode`（八进制）、`uid`、`gid`、`size`。
- 会话结束时 `commit()` 写 `manifest.json`（`createdAt`、`scriptName`、`targetSummary`、`directoryPath`、`entries`、`restoredAt`），并加入记录页的备份列表。

**哪些操作会被备份**：`replace` / `copy` / `move` 的 `dest`（**仅当它已存在时**）、`delete` 的 `dest`。`mkdir`、`chmod`、`chown`、`kill`、`note` **不产生备份条目**。

**`replace` 的 dest 原本不存在时**也会登记一条 `existed: false` 的条目——这正是回滚时能把它删掉的原因。

### 5.2 回滚做了什么

`RunStore.restore(record)` 逐条处理 `entries`：

| 条目的 `existed` | 回滚动作 |
| --- | --- |
| `true` 且 `relativePath` 非空 | 先把原路径的父目录属主改成 `mobile:mobile`；原路径存在就先删掉；再把 `files/...` 里的原件拷回原路径；然后恢复 `mode`（`DSKernel.setMode`）和 `uid:gid`（`DSKernel.setOwner`，非递归）。 |
| `true` 但 `relativePath` 为空（当时没备份成功） | 记一条失败：「备份文件缺失：<路径>」，继续处理其它条目。 |
| `false` | 视为「脚本新建的文件」：如果它还在，就删掉它。 |

- 回滚结束会把 `restoredAt` 写回 `manifest.json`，记录页那条备份会显示「已回滚过」。
- 只要有任意一条失败，会抛 `部分文件回滚失败：...`（成功的那些**已经改完了，不会自动退回**）。
- 回滚**不会**恢复：`chmod` / `chown` 改过的权限与属主（这些没进备份）、被删除后又新建的内容、以及内核层面的任何状态。
- 删除备份 = 整份移除备份目录，之后**永久无法再回滚这次改动**（记录页会二次确认）。
- 另外注意：文本编辑器保存文件时用的是**另一套**机制——在原文件旁留 `<文件名>.dsfbak`，跟这里的备份会话无关，不会被记录页管理。

### 5.3 运行历史

每次预演/执行/Shell 运行都会写：

```
<App Documents>/Runs/<yyyyMMdd-HHmmss>-<脚本名>.json   ← RunRecord
<App Documents>/Runs/<yyyyMMdd-HHmmss>-<脚本名>.log    ← 纯文本日志
```

`RunRecord` 字段：`id`、`date`、`scriptName`、`scriptKind`、`targetSummary`、`success`、`dryRun`、`summary`、`backupId`、`logPath`。记录页可以看详情、分享日志、删除（删除会连 `.log` 一起删）。

## 六、预演（dry-run）会检查什么、不会做什么

### 会做（`preflight()` + 逐步走一遍）

1. **激活状态**：`DSKernel.isEscaped()` 为假 → 警告「尚未激活内核访问：涉及沙盒外路径的操作会失败。请到设置页点『激活』。」
2. **目标是否缺**：步骤里出现 `{app.` 但没有解析出目标 → 报错。
3. **步骤非空**：`steps` 为空 → 报错。
4. **逐步骤静态检查**：
   - `op` 不认识 → 「第 N 步的操作名不认识：xxx」；
   - `replace` / `copy` / `move` 缺 `source` → 报错；
   - 除 `kill` / `note` 外缺 `dest` → 报错。
5. **逐步执行检查阶段的行为**（`perform(..., apply: false)`）：
   - `replace`/`copy`/`move`：源不存在时，`optional: true` → 跳过，否则 → **失败**；目标存在与否只影响文案（「将覆盖已有文件」/「新建」）；
   - `mkdir`：只报「将创建」或「目录已存在」；
   - `delete`：目标不存在时，`optional: true` → 跳过，否则 → **失败**；
   - `chmod`/`chown`：只做参数完整性检查（`dest`/`mode`、`dest`/`owner`），**不会去读文件是否真的存在**；
   - `kill`：只报「结束 <name>」，不真的杀进程。
6. 最后给结论：`预演通过：可以执行。` 或 `预演发现 N 个问题。`；同时在「记录」页留下一条 `dryRun: true` 的运行记录。

### 绝对不会做

- 不创建、不修改、不删除、不改权限、不改属主、**不结束任何进程**；
- **不创建备份会话**（`backupId` 为 nil，不会在 `Documents/Backups` 下留目录）；
- 不写任何 `manifest.json`。

> 换句话说：预演是「只看不动」。但它**也不能保证**真跑时一定成功——比如 `chmod` 的目标不存在、磁盘空间不够、内核状态在中途掉了，这些只有执行时才会暴露。

## 七、Shell 脚本

### 7.1 它是什么

脚本详情页里 `kind == .shell` 的那些脚本，点击「运行脚本」后由 `ShellScriptRunner` 调 `DSShell`：

- 执行方式：`posix_spawn("/bin/sh", [脚本路径])`（先检查 `access("/bin/sh", X_OK)`）；
- **工作目录**：脚本自己所在的目录（`{script.dir}`）；
- **超时**：`120` 秒（`run(timeout: 120)`）；超时会 `SIGKILL` 掉子进程并报「脚本执行超时（120 秒），已强制结束」；
- 输出：stdout 和 stderr 合并回显在脚本详情页的「脚本输出」区域（按行实时追加），同时也写进这次运行的 `.log`；
- 退出码：0 算成功；被信号结束会报「脚本被信号 N 结束」。

### 7.2 可用环境变量

以下变量就是 `ScriptLibrary.shellTemplate` 里列出的那套（由 `ShellScriptRunner.run` 注入）。目标是手动选的或从配方 `target` 解析出来的，取决于当前脚本对应的目标：

| 变量 | 内容 |
| --- | --- |
| `DS_TARGET_BUNDLE` | 目标 App 包体路径 |
| `DS_TARGET_DATA` | 目标 App 数据容器路径 |
| `DS_TARGET_BUNDLE_ID` | 目标 App bundle id |
| `DS_TARGET_EXEC` | 目标可执行文件路径 |
| `DS_SCRIPT_DIR` | 本脚本所在目录 |
| `DS_SCRIPT_NAME` | 脚本名（也会注入，但模板注释里没写） |

另外 `DSShell` 会自动补两个变量（如果环境里没有）：`PATH=/usr/bin:/bin:/usr/sbin:/sbin`、`HOME=<App 的 Home>`。

> 目标没解析出来时，`DS_TARGET_*` 四个变量**根本不会注入**，脚本里引用会是空字符串（建议用 `${DS_TARGET_DATA:-}` 这种写法兜底）。

### 7.3 免越狱下可能起不来（EPERM）与替代方案

`posix_spawn` 失败时，如果 `rc` 是 `EPERM` 或 `EACCES`，App 会追加这段说明：

> 沙盒拒绝了 process-exec。免越狱 + DarkSword 环境下这是预期行为：shell 脚本需要越狱 / TrollStore 环境，或改用配方脚本。

**替代方案（按推荐顺序）**：

1. **改用配方脚本**：把 `cp` 换成 `replace`、`mkdir -p` 换成 `mkdir`、`rm -rf` 换成 `delete`、`chmod` 换成同名 op。配方在 App 进程内直接调文件 API，不依赖 `process-exec`，而且**有预演、有备份、可回滚**。Shell 脚本这三样都没有。
2. **用「文件」页手动操作**：属性面板能改名、复制一份、移动、删除、改权限、改属主，相当于交互式的 `mv`/`cp`/`rm`/`chmod`/`chown`。
3. **在越狱 / TrollStore 环境里跑同一个 `run.sh`**：那里 process-exec 是通的。

### 7.4 官方 Shell 模板

新建 Shell 脚本时生成的内容（原文，`ScriptLibrary.shellTemplate`）：

```sh
#!/bin/sh
# myfilza Shell 脚本
# 运行时可用环境变量：
#   DS_TARGET_BUNDLE     目标 App 包体路径
#   DS_TARGET_DATA       目标 App 数据容器路径
#   DS_TARGET_BUNDLE_ID  目标 App bundle id
#   DS_TARGET_EXEC       目标可执行文件路径
#   DS_SCRIPT_DIR        本脚本所在目录
#
# 注意：免越狱 + DarkSword 环境下沙盒可能仍拒绝执行进程，
# 这时 posix_spawn 会直接失败 —— 请改用配方脚本。

set -e
echo "目标: $DS_TARGET_BUNDLE_ID"
echo "包体: $DS_TARGET_BUNDLE"
echo "数据: $DS_TARGET_DATA"

# cp -f "$DS_SCRIPT_DIR/payload/config.json" "$DS_TARGET_DATA/Documents/config.json"
```

## 九、三个可直接粘贴运行的完整示例

用法都一样：脚本页 → 新建脚本（配方）→ 把下面 JSON 整个贴进「编辑脚本内容」→ 保存 → 添加 payload 文件 → 选目标 App → 预演 → 执行。

### 示例 ①：只替换数据容器里的一个配置文件

场景：某个 App 的配置文件在它自己的数据容器里（沙盒外），你想换成自己的版本，跑完让它重启加载。

```json
{
  "schema": 1,
  "name": "替换某个 App 的配置文件",
  "note": "只碰数据容器里的 Documents/config.json；覆盖前会整份备份，随时可在记录页回滚。",
  "target": { "bundleId": "com.example.target" },
  "options": { "backup": true, "killTarget": true, "stopOnError": true, "fixOwnership": true },
  "steps": [
    { "op": "note", "note": "第 1 步：确认备份开关是开的——关掉就没有回滚兜底了。" },
    { "op": "mkdir", "dest": "{app.data}/Documents" },
    { "op": "replace", "source": "payload/config.json", "dest": "{app.data}/Documents/config.json" },
    { "op": "chmod", "dest": "{app.data}/Documents/config.json", "mode": "0644" },
    { "op": "kill" }
  ]
}
```

配套操作：把你要用的 `config.json` 通过脚本详情页的「添加 payload 文件」放进 `payload/`（文件名必须和 `source` 里写的一致）。

要点：
- `mkdir` 对已存在的目录是无害的（会报「目录已存在」并继续）；
- `chmod` 走内核接口，所以即使文件原来属主是 root 也能改；
- `kill` 用 `CFBundleExecutable` 匹配进程，杀不到只是「跳过」，不算失败。

### 示例 ②：替换 App 包体里的一个资源图片并 chmod

场景：换掉某个 App 包体里的图片资源。**只动图片这类资源文件，不要动主可执行文件。**

```json
{
  "schema": 1,
  "name": "替换 App 包体里的一个资源图片",
  "note": "覆盖 .app 里的 AppIcon60x60@2x.png，并把权限改成 0644。资源文件被改不会破坏签名校验链里最关键的可执行文件——但如果你改的是别人 App，请确认你有权这么做。",
  "target": { "bundleId": "com.example.target" },
  "options": { "backup": true, "killTarget": true, "stopOnError": false, "fixOwnership": true },
  "steps": [
    { "op": "replace", "source": "payload/AppIcon60x60@2x.png", "dest": "{app.bundle}/AppIcon60x60@2x.png" },
    { "op": "chmod", "dest": "{app.bundle}/AppIcon60x60@2x.png", "mode": "0644" },
    { "op": "replace", "source": "payload/extra-icon.png", "dest": "{app.bundle}/extra-icon.png", "optional": true },
    { "op": "kill" }
  ]
}
```

要点：
- 目标 App 必须是**已经安装**的，代码里的包体路径来自 `/var/containers/Bundle/Application/<UUID>/<名字>.app`；
- `{app.bundle}` 下的内容属于 App 包体，写之前通常要让父目录对 `mobile` 可写——`fixOwnership: true` 就是在干这件事；
- 第 3 步演示 `optional: true`：源文件不存在时记「跳过」而不是失败，适合「有这个文件就换、没有就算了」的场景；
- 这里 `stopOnError: false`：即使第 3 步出问题也把后面的 `kill` 跑完。
- **重点风险**：目标是自签安装时，改 `{app.bundle}` 里的东西会让签名校验失败。资源文件可能导致 App 直接打不开（若校验覆盖整包），最坏情况需要重装——动手前先确认你有备份和重装手段。

### 示例 ③：删除 + 新建 + 结束目标 App 的组合

场景：清掉某个 App 的一个缓存/标记文件，建一个新的空占位文件，再把它重启。这个示例把所有 op 都用一遍做参考。

```json
{
  "schema": 1,
  "name": "清缓存 + 重建占位 + 重启目标 App",
  "note": "删掉标记文件、建一个空目录和一个空文件、改权限属主，最后结束目标 App。删除前会先备份原件。",
  "target": { "bundleId": "com.example.target" },
  "options": { "backup": true, "killTarget": true, "stopOnError": true, "fixOwnership": true },
  "steps": [
    { "op": "note", "note": "1) 删掉旧的标记文件；不存在就跳过，不报错。" },
    { "op": "delete", "dest": "{app.data}/Library/Preferences/marker.plist", "optional": true },

    { "op": "note", "note": "2) 建一个新的缓存目录，并准备一个空占位文件。" },
    { "op": "mkdir", "dest": "{app.data}/Library/Caches/dsfile-placeholder" },
    { "op": "replace", "source": "payload/placeholder.txt", "dest": "{app.data}/Library/Caches/dsfile-placeholder/keep.txt" },
    { "op": "chmod", "dest": "{app.data}/Library/Caches/dsfile-placeholder/keep.txt", "mode": "0644" },
    { "op": "chown", "dest": "{app.data}/Library/Caches/dsfile-placeholder/keep.txt", "owner": "mobile:mobile" },

    { "op": "note", "note": "3) 把自己的一份配置拷进去（不覆盖原来不存在的位置也不算失败）。" },
    { "op": "copy", "source": "payload/extra.conf", "dest": "{app.data}/Documents/extra.conf", "optional": true },

    { "op": "note", "note": "4) 结束目标 App，让它下次启动重新读配置。" },
    { "op": "kill" }
  ]
}
```

要点：
- `delete` 用 `optional: true` 时，目标不存在 → 「跳过」，不会中断；
- 配了 `kill` 步骤后，`options.killTarget` 就**不会**再额外杀一次（不会重复杀）；
- `chown` **非递归**：只改你写的那个 `dest`，子项不动。要递归改属主，去「文件」页的属性面板开「递归」；
- 想让「脚本新建的文件」在回滚时被自动删掉，就正常走 `replace`/`copy`（它们会给不存在的 `dest` 登记 `existed: false` 条目）；但 `mkdir` 建的目录**不进备份**，回滚不会删它，需要你手动清理。

## 十、脚本包怎么组织与导入

### 10.1 目录结构（推荐这么打包）

```
我的脚本/
├── recipe.json        ← 或任意 .json；Shell 脚本则是 run.sh（或任意 .sh）
└── payload/
    ├── config.json
    └── AppIcon60x60@2x.png
```

### 10.2 三种导入方式

| 入口 | 支持什么 | 行为 |
| --- | --- | --- |
| **导入脚本包（文件夹）** | 一个目录 | 目录里有 `recipe.json` → 按配方导入；没有 `recipe.json` 但有 `.sh` → 按 Shell 导入；没有 `.sh` 但有 `.json` → 按配方导入；都没有 → 报错「这个文件夹里既没有 recipe.json，也没有 .sh 脚本」。**整个目录（含 `payload/`）会递归拷进脚本库**，脚本名取目录名。 |
| **导入脚本文件** | `.json` / `.sh` / `.txt`，可多选 | 类型判定：`.sh` → Shell；`.json` → 配方；其它看前 200 个字符去掉空白后是不是以 `{` 开头，是 → 配方，否则 → Shell。脚本名取文件名（去掉扩展名）。`.json` 会保留原文件名。 |
| **新建脚本** | — | 生成一份模板（配方用官方模板，Shell 用 `shellTemplate`），并自动建好 `payload/` 目录。 |

### 10.3 payload 怎么进去

| 方式 | 说明 |
| --- | --- |
| 脚本详情页「添加 payload 文件」 | 多选文件（或目录），拷进 `<脚本目录>/payload/`；**重名时自动生成 `xxx-1.ext` 这类不冲突的名字**，并且会提示实际文件名——所以替换重名文件时要小心看列表里的真实名字。 |
| 「文件」页手动拷 | 因为 Documents 在系统「文件」App 里可见，你可以直接往 `Documents/Scripts/<脚本目录>/payload/` 拖文件。 |
| 整包导入 | 用「导入脚本包」，`payload/` 会跟着一起进来。 |

脚本详情页的 payload 区域会列出当前 payload 里的文件（名称 + 大小），每项右侧有删除按钮；脚本列表行也会显示「payload N 项」。

### 10.4 几个容易踩的坑

1. **相对路径是相对脚本目录，不是相对 payload 目录**：写 `payload/x.png`，不要写 `x.png`（`x.png` 会被解析成 `<脚本目录>/x.png`，通常不存在 → 预演报「源文件不存在」）。
2. **`payload` 目录名是写死的**：`{script.payload}` 就是 `<脚本目录>/payload`。
3. **改了配方里的 `options` 会重写 `recipe.json`**：注释没了，键顺序按字母排。如果你想手写保持原样，就少用界面上的开关。
4. **配方里不要写 `{app.executable}` 当 `dest`**，除非你清楚后果（见 README「不能做什么」第二条）。
5. **不确定就先预演**：预演不改任何文件、不留备份目录，但会把所有静态问题一次性列出来。
