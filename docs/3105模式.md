## 一、3105 的漏洞到底是什么

3105 是**两条腿**：内核漏洞 + 沙盒扩展令牌。两者用途不同。

1. **内核读写**：`kexploit/kexploit_opa334.m` —— 与我们现有后端**同源**（DarkSword / CVE-2025-43520，
   经 opa334 / Dopamine 研究传承，注释里也承认了 FilzaSlop、CrazyMind90、forcequitOS 的贡献）。
   它做的是「竞态 + 物理页越界（OOB）读写」，成功后得到**任意内核读写**。
   - 前置条件：无特殊 entitlement，普通证书签名的 App 即可；**需要真机**（模拟器不可用）。
   - 与我们现有后端的关键差异**不在漏洞本体，而在 offset 表**：3105 的 `offsets.m` 是 49,641 字节，
     覆盖到 iOS 26.x / 27 beta；我们现有的 FilzaJailedDS 2.2 那份是 51,065 字节但只覆盖 17.x–18.x。
2. **沙盒扩展令牌（不是内核漏洞）**：`exploit/bad_query.c` —— 用 ContainerManager（MCM）的
   `container_query` 做**路径穿越**（`part_domain` 传 `../../../../../../../..<路径>`，
   类 13 = `systemgroup.com.apple.mobilegestaltcache`，或类 7 + 指定 group id），
   再 `container_copy_sandbox_token()` 拿到令牌、`sandbox_extension_consume()` 消费它，
   从而**给自己签发任意路径的沙盒扩展**（读写权限）。
   - 这是**纯用户态**的越权：不需要内核漏洞就能拿到沙盒外文件访问。
   - 前置条件：无特殊 entitlement；但只在系统漏洞未被修掉的版本上有效。
   - 另附 `bad_query_list()`：用 `fsgetpath` 按 inode 扫描列出目录（读不到权限时也能列名字）。
3. **3105 自己的策略**（`helpers/KernelExploit.swift` + `SupportPolicy.swift`）：
   `kexploit_opa334()` → `proc_self()` → `sandbox_escape(proc)`；
   **iOS < 26**：拿到内核读写就算「可用」（文件浏览退化为 LSApplicationWorkspace + inode 扫描）；
   **iOS ≥ 26**：必须沙盒逃逸成功（走 bad_query 那条路）。

一句话：**3105 = 同源内核漏洞（更新 offset 表）+ 自己那份 sandbox_escape + bad_query 令牌越权**。

## 三、它的文件访问机制 / 文件替换流程

- **内核层**：`kread64/kwrite64` 等原语（`krw.m`）+ `sandbox_escape.m` 改 cred→label→sandbox→ext_set，
  与我们现有思路一致（都源自 FilzaSlop 那套）。
- **令牌层**：`bad_query()` 直接给出沙盒扩展句柄；`mcm_bridge.m` 把 MCM 的
  「枚举标识符 / 取容器路径 / 激活容器路径」包装成 ObjC 接口，供它自己的文件浏览器用。
- **文件替换**：`helpers/FileReplacementService.swift` 只是**在拿到访问权限之后**做常规文件操作
  （读源、写目标、按 patch 事务回滚），**不包含第二套沙盒逃逸**。
  → 所以我们**不需要**照搬它的替换逻辑：本 App 的替换 / 备份 / 回滚继续走我们自己的
  `RecipeRunner` + `RunStore`，3105 只负责「取得文件系统访问」这一件事。

## 六、用法

1. 设置 → **内核模式**：选 `FilzaJailedDS 2.2`（默认）或 `3105`；
   - 每一行都会显示**适用范围**、你的设备/系统是否**在范围内**，以及一句推荐；
   - 如果所选模式不在范围内，激活前会给出橙色提示 + 一个「切换到另一个模式」按钮。
2. 回到「内核访问」→ 点**激活内核访问**（入口只有一个，内部按所选模式分派）。
3. 3105 模式有**两条路径**，默认走安全的那条：
   - **默认（推荐）**：纯用户态令牌 —— 日志为 `用户态令牌：开始取令牌` → `取到 N/M 条` → 探针验证。
     **完全不执行内核代码**，不会自旋、不会重启；
   - **可选（需显式开启）**：设置 → 内核模式 → 3105 下面的「使用内核漏洞」开关。开启后日志为
     `内核阶段：kexploit_opa334（只取内核读写）` → 再走同一条用户态令牌路径。
     **不会调用** 3105 的 `proc_self` / `sandbox_escape`（原因见第九节）。
4. 日志会写明用的是哪个模式、跑到哪一阶段，并写进 `Documents/Logs/kernel-breadcrumb.log`；
   开启内核路径时，**在调用之前**就会先写一行面包屑 + 一行会话日志（两者都 fsync 过）。
5. 切换模式后**需要重新激活**（两套后端各自独立，不会互相复用状态）。
6. **安全模式**（设置 → 内核模式里的总开关，**默认关**）：开启后**任何模式都不执行内核漏洞**——
   3105 强制只走用户态令牌；FilzaJailedDS 因为整体依赖内核漏洞会被**阻止执行**并提示改用 3105。
   适合「宁可能力受限，也绝不重启」的场景。
7. **适用性检查**：所选模式超出它声明支持的范围时，**不会硬跑内核阶段**，而是只走用户态令牌，
   并在日志里写明「已跳过内核阶段」及原因。

## 七、隔离做法（为什么不会互相影响）

- **只做加法**：`FilzaTweak/**`、`kexploit_*`、`DSCredEscape*` 一行未改；默认模式的代码路径与 0.4.0 逐字一致。
- **唯一分派点**：`DSKernel.m` 的 `activateWithLog:` 里加了一个 `if (DS3105KernelSelected())` 分支，
  选中 3105 时直接返回、**绝不进入**下面 FilzaJailedDS 的逻辑；未选中时该条件恒为假。
- **符号隔离**：3105 自带一份与我们同名的 `kexploit_opa334` / `krw` / `offsets`，两者必须共存于同一个
  可执行文件，所以新增 `DS3105SymbolPrefix.h` 把 3105 侧 **216 个自有符号**统一改名为 `t3105_*`，
  并通过 XcodeGen 的 `compilerFlags: -include …` **只作用于 `Vendor/ThreeOneOSFive` 下的源文件**。
- **不共用原语**：`DS3105Kernel.m` 只调用 3105 自己的入口，不调用也不暴露我们的 `kread/kwrite`；
  它的就绪状态是自己的静态变量，与现有后端的 `gEscaped` 无关。
- **共用（有意为之）**：设置页 UI、激活入口的那一处分派、「沙盒外写探针」与
  `myfilza.fileSystemAccessChanged` 通知（这样替换页/应用管理器不必关心用的是哪个后端）。
- **头文件不串台**：3105 的目录**没有**加进 `HEADER_SEARCH_PATHS`（两套后端各有一份 `krw.h`/`offsets.h`，
  加进去就可能互相解析错）；3105 自己的源文件靠「同目录优先」解析自己的头，
  适配层 `DS3105Kernel.m` 则用显式相对路径包含 3105 的头。

## 八、已知边界

- 3105 的失败路径会调用它自己的 `kexploit_abort()`：在漏洞阶段内是 `longjmp` 回调用点
  （上游注释写明 "app stays alive"），只有漏洞阶段之外才会 `exit()`。**未修改**这个行为。
- **3105 的 `proc_self` / `sandbox_escape` 在本项目里被完全禁用**：它们在
  `so_background_thread == 0` 的机型上会让 3105 的 `early_kread` 原地自旋、被系统 watchdog 杀掉进程
  （设备不重启、也无崩溃日志）。这就是 0.5.1 修掉「3105 模式一跑就闪退」的方式，详见第九节。

## 九、bad_query：纯用户态的容器访问（3105 模式的默认路径）

### 机制
`exploit/bad_query.c` 的 `bad_query(path, create, group_identifier, is_group)` 全程在用户态完成：

1. `dlopen("/usr/lib/system/libsystem_containermanager.dylib")` + `dlsym` 取私有符号；
2. `container_query_create` → `container_query_set_class(13)`（`group_identifier == NULL` 时用
   `systemgroup.com.apple.mobilegestaltcache`）→ `container_query_operation_set_part(3)` →
   `container_query_operation_set_part_domain("../../../../../../../.." + path)`（**路径穿越**）→
   `container_query_operation_set_flags(0x8000000000)`；
3. `container_query_get_single_result` → `container_copy_sandbox_token` 拿到沙盒扩展令牌；
4. `sandbox_extension_consume(token)` → 返回句柄（进程内保持有效，不主动 release）。

### 是否依赖内核漏洞：**不依赖**（源码取证）
`bad_query.c` 与 `mcm_bridge.m` 里**没有任何内核原语**——grep
`early_kread|kread|kwrite|kexploit|krw|kaddr|proc_self|offsets` **0 命中**；
它们只依赖 `dlopen` / `dlsym` / `xpc` / `sandbox_extension_consume`。
所以「仅用户态令牌」在**完全不跑内核漏洞**的前提下也能拿到容器访问。

### 我们请求令牌的路径（顺序）
`/var/mobile` → `/var/mobile/Containers/Data/Application` → `/var/containers/Bundle/Application`
（不存在的路径跳过；最多缓存 16 条）。替换目标在别处时，可用
`DS3105KernelEnsureAccessForPath(path)` 按需补取一条。

### 为什么**不能**调用 3105 的 `proc_self` / `sandbox_escape`
真机实测（iPhone13,4 / iOS 18.5）：

```
[+] win??                                                        ← 内核漏洞成功
[t3105_early_kread:463] kaddr isn't valid, spinning here. kaddr: 0x388
  #0 t3105_early_kread + 204   #1 t3105_early_kread64 + 28
  #2 t3105_proc_self + 96      #3 DS3105KernelActivate + 384
```

本机 `so_background_thread == 0` → `proc_self()` 拿 0 当 thread 去读
`off_thread_t_tro`（= 0x388）→ 非法地址 → 3105 的 `early_kread` 在这里是**原地自旋**
（不是返回失败）→ 被系统 watchdog 杀掉进程（设备**不重启**、也**没有崩溃日志**）。
`sandbox_escape` 内部同样要经过 proc / label 链路，所以一并禁用。

> 我们**不改** 3105 源码（GPL 保真），做法是**不调用**这些会拿 0 / 无效地址去读内核的函数。

### 我们目前实际调用的 3105 函数（全部，0.6.0 起）

| 函数 | 何时调用 |
| --- | --- |
| `kexploit_opa334()` | **默认调用**（0.6.0 起）：只取内核读写，供 cred 路线逃逸使用 |
| `kread64/kread32/kwrite32/early_kread/early_kwrite32bytes` | 同上：cred 路线逃逸与提权用的原语 |
| `bad_query()` | **备选分支**（内核失败或用户关掉内核档时）；18.x 上因缺符号会返回 -1 |
| `MCMBridgeAvailable()` | 只做一次可用性探测并写日志（不依赖它） |

其余 3105 代码（`proc_self`、`sandbox_escape`、`vnode`、`wallpaper_zip` 等）**一律不调用**。

- 两个后端都不覆盖：`/System`、`/usr` 等 SSV 签名卷仍只读。
- 3105 声明支持的 27 beta 是按 **build 白名单**判定的（24A5355q / 24A5370h / 24A5380h / 24A5390f）；
  其它 27 build 不在其声明范围内（我们仍允许尝试，但会在日志里警告）。

## 十、0.6.0：18.x 上真正能用的那条路（内核 R/W + cred 路线逃逸）

### 结论（真机 + 源码取证）
- **3105 本体在 iOS < 26 时不用 bad_query**：它的 `KernelExploit.swift` 写明「iOS < 26：拿到内核 R/W 就算 Active 状态，文件浏览回退到 LSApplicationWorkspace + inode walk；iOS 26+ 才需要沙盒逃逸（bad_query 路径）」。
- **bad_query 在 18.5 上必然失败**：`libsystem_containermanager.dylib` 里没有 `container_query_operation_set_part` / `…_set_part_domain` 两个符号（日志里的 `set_part=0x0 set_part_domain=0x0` 就是证据），而 `bad_query.c` 是**全有或全无**校验 → 直接返回 -1、0 条令牌。
- 3105 本体之所以能访问别的 App 容器，在 18.x 上靠的是**内核 R/W + vnode/inode 层**，而不是用户态令牌。
- 另：上游 `Info.plist` 的 `CFBundleIdentifier` 是 `com.apple.mobile.MobileHouseArrest`（伪装成 Apple 的容器访问守护进程），`mcm_bridge.m` 的激活路径也硬校验这个 bundle id —— 这条路我们**不采用**（要求改包名，且只有 26+ 才需要）。

### 我们 0.6.0 的做法（= 当年 Filza 那条路上成功的那套，原语换成 3105 的）
1. **内核阶段**：3105 自己的 `kexploit_opa334()`（运行时反推 offset），只取内核读写；
2. **逃逸阶段**：**cred 路线** —— 两个 socket 的 `so_cred` 指向同一对象 + `kread32(cred+0x18) == getuid()`（有界扫描 0x1f0~0x230，历史命中 `socket+0x208`）→ `label = S(kread64(cred+0x78))` → `sandbox = S(kread64(label+0x10))` → `ext_set = S(kread64(sandbox+0x10))` → 照抄上游三步改写（ext 的 data 指向的字符串改 `/`；`da+32` 写 `com.apple.app-sandbox.read-write`；`da+64` 清零；`hdr+0x10 = da+32`；16 个空槽填第一个 header）；
3. **XPACI 无条件裸汇编**（`.long 0xDAC143E0`）：3105 的 `S()` 宏只在 `#ifdef __arm64e__` 下才编译出真指令，而本 App 产物是 arm64 —— 直接用它会把带 PAC 签名的 `cr_label` 解引用到错误地址；
4. `bad_query` 降级为**备选分支**；日志里会标明走的是哪条；
5. 两个阶段**互相独立**：内核阶段失败**不中止**容器访问阶段，最终失败信息**同时列出**两阶段各自原因；
6. **提权按后端分派**：3105 模式下用 `t3105_kread*/t3105_kwrite*` 改写 cred（不再误用 FilzaJailedDS 的原语，避免拿未初始化原语野读）。

### 结构性证据（本包已核对）
- 主二进制里 `t3105_proc_self` / `t3105_sandbox_escape` **已不存在**（无人调用 → 链接器 dead-strip）→ 那个会自旋、被 watchdog 杀进程的入口在包里**物理上不可达**；
- 主二进制里可搜到 `stage1: kexploit_opa334` / `stage2: cred route escape` / `stage3: userspace tokens` / `elevate: cred=` 等新日志串。

### 每跳的安全闸门（照旧）
内核地址校验 + zone 段（`0xffffffc000000000`–`0xfffffff000000000`）+ 8 字节对齐；**不扫描、不猜地址**；任何一跳不成立就**干净返回失败**，并把「阶段 + 原始值/还原值」写进日志与面包屑（纯 ASCII，避免 stdout 捕获时的编码问题）。
