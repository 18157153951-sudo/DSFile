# 3105 本体分析：它在 iOS 18.5 上凭什么访问别人的容器

> 分析对象：用户提供的 3105 未签名 IPA（`Payload/3105.app/3105`，5.87 MB 主可执行）
> ＋ 上游源码 `github.com/YangJiiii/3105`（本仓库 `DSFile/Vendor/ThreeOneOSFive/` 内为逐字节原样副本）
> 分析环境：Windows（无 `otool`/`nm`，改用 Mach-O 字符串/符号扫描 ＋ 源码阅读；命令清单见文末）

## 一、结论（一句话）

**3105 把自己的 bundle id 伪装成 `com.apple.mobile.MobileHouseArrest`（Apple 自己的容器访问守护进程）。**
iOS 因此给它一个**特权沙盒 profile**：**不跑任何漏洞**就能写 `/private/var/mobile/...`；
MobileContainerManager（MCM）也愿意把**别的 App 容器的沙盒扩展令牌**发给它。
拿到令牌并 `sandbox_extension_consume` 之后，它用**普通 POSIX / Foundation 文件 API** 读写目标容器
—— **不需要 vnode 技巧，也不需要特殊 entitlement**。

## 二、证据

### 证据 1（最关键）：上游源码注释自己承认

`DSFile/Vendor/ThreeOneOSFive/kexploit/sandbox_escape.m`，函数 `sandbox_access_is_active()` 内：

> Probing `/var/mobile` was a false positive: **the MobileHouseArrest sandbox permits writes there without
> any exploit**, so the app "detected" active access at launch, skipped the kernel exploit, and every
> privileged feature then failed (MCM handed out no sandbox tokens, bad_query grants returned -1).

即：**仅凭这个 bundle id 带来的沙盒 profile，`/private/var/mobile` 就是可写的** —— 上游自己踩过这个坑。

同处探针实现（`probe_write_read_delete`）会依次对
`/private/var/mobile/Containers/Data/Application`、`/private/var/mobile/Containers/Data/System`
做 `open(O_RDWR|O_CREAT|O_EXCL)` → `write` → `lseek` → `read` → `close` → `unlink`，全通过才算"访问生效"。

### 证据 2：MCM 路径有硬门槛（bundle id）

`DSFile/Vendor/ThreeOneOSFive/exploit/mcm_bridge.m:289`：

```objc
NSString *MCMActivateContainerPath(uint64_t cls, NSString *identifier, BOOL group, NSString **error) {
    if (![NSBundle.mainBundle.bundleIdentifier isEqualToString:@"com.apple.mobile.MobileHouseArrest"]) {
        if (error) *error = @"host bundle identifier is not com.apple.mobile.MobileHouseArrest";
        return nil;
    }
    ...
```

随后调用序列（库来自 `dlopen("/usr/lib/system/libsystem_containermanager.dylib")`）：

`container_query_create` → `container_query_set_class` → `set_identifiers` / `set_group_identifiers`
→ `container_query_operation_set_flags` → `container_query_get_single_result` → `container_object_get_path`
→ **`container_copy_sandbox_token`** → **`container_object_sandbox_extension_activate`**
→ 最后用**普通 `open(rootPath, O_RDONLY|O_DIRECTORY|O_CLOEXEC|O_NOFOLLOW)` 验证**（成功即视为拿到访问）。

### 证据 3：用户那份 IPA 的 bundle id 就是它

从 `Payload/3105.app/Info.plist`（二进制 plist）扫描到 `CFBundleIdentifier` 的值为
`com.apple.mobile.MobileHouseArrest`。

主二进制字符串命中次数：

| 字符串 | 次数 |
| --- | --- |
| `com.apple.mobile.MobileHouseArrest` / `MobileHouseArrest` | 3 / 3 |
| `sandbox_access_is_active` | 1 |
| `libsystem_containermanager` | 1 |
| `container_query` | 11 |
| `container_copy` | 1 |
| `sandbox_extension_consume` | 1 |
| `bad_query` | 15 |
| `vnode` / `inode` | 10 / 3 |
| `LSApplicationWorkspace` | 2 |
| `kexploit_opa334` / `sandbox_escape` | 5 / 6 |

### 证据 4：文件读写都是普通 API（说明"进程本身就有访问"）

- `helpers/FileManagerService.swift`：`FileManager.copyItem`、`FileHandle(forReadingFrom:)`、`open(...)`
- `helpers/FileReplacementService.swift`：`FileHandle(forReadingFrom:)` / `FileHandle(forWritingTo:)`
- `helpers/ContainerStore.swift:493`：`fopen(metadataPath, "r")` 直接读**别的容器**的 MCM 元数据
- `ContainerStore.swift:107` 注释也点明：iOS 18.1.x 这类"MCM 不发令牌"的版本，它退化成
  **inode walk + 直接读元数据 plist**，而"raw reads only succeed when the sandbox escape is active"

→ 结论：它靠的是**进程身份带来的沙盒权限**，不是 vnode 层绕行（`vnode.m` 存在，但用于其它功能）。

## 三、为什么 `bad_query` 在 18.5 上必然失败（解释我们早前的失败）

1. `exploit/bad_query.c` 需要 `container_query_operation_set_part` 与 `…_set_part_domain`；
   **这两个符号在 iOS 18.5 的 `libsystem_containermanager.dylib` 里不存在**
   （真机日志：`set_part=0x0 set_part_domain=0x0`），而它是"全有或全无"校验 → 直接 `-1`、0 条令牌。
2. 上游 `helpers/KernelExploit.swift`：`requiresSandboxEscape = majorVersion >= 26`
   → **bad_query 是 iOS 26+ 的路径**；< 26 时它拿到内核 R/W 就 return true，
   文件浏览走 **MHA 沙盒 profile ＋ MCM 令牌**（必要时加 inode walk）。

所以：**18.x 上真正起作用的是"bundle id 身份"，内核 R/W 是给其它功能用的**；
`sandbox_escape` 返回 -1 也不影响它浏览容器（这正是用户实测到的现象）。

## 四、能否复刻 / 建议路线

### 路线 A：换 bundle id（最省事、最稳，推荐评估）

把 myfilza 的 bundle id 改成 `com.apple.mobile.MobileHouseArrest`（或另出一个用该 id 的构建）
→ 大概率**不跑内核**就能获得宽泛文件访问 ＋ MCM 容器令牌。

- 代价：bundle id 变更 = 新 App，**现有安装的脚本/备份/日志不会继承**（需要迁移或导入导出）；
- 风险/性质：属于**身份伪装**（用户自有设备，由用户决定是否采用）；
- 未验证项：MCM 是否**额外**校验 entitlement。倾向"不需要"——因为 3105 在用户机器上是
  证书重签安装后即可用的（重签会替换私有 entitlement）。

### 路线 B：注入 3105（已在并行进行）

把我们的替换引擎做成 dylib 注入 3105 进程：宿主 bundle id 本来就是 MHA，
天然享有该沙盒 profile → 我们的代码只做普通 POSIX 读写即可，**同样不需要内核**。
